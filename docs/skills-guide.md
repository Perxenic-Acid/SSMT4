# Matt Pocock 技能使用指南

本项目安装了 13 个 Matt Pocock 的 Agent 技能。所有技能通过 `/技能名` 的方式调用。

---

## 工程类技能（日常开发使用）

### /diagnose — Bug 诊断

**用途**：系统化地排查难以定位的 Bug 或性能回归。

**流程**（6 个阶段）：
1. **构建反馈回路** — 创建一个能快速复现 Bug 的自动化手段（测试脚本、curl 命令、CLI 调用等）。这是最核心的步骤，2 秒出结果的确定性回路比 30 秒的不可靠回路强 100 倍。
2. **复现** — 确认反馈回路能稳定复现用户描述的 Bug。
3. **假设** — 生成 3-5 个可证伪的假设，每个假设需包含预测："如果是 X 导致的，那么改变 Y 会让 Bug 消失"。
4. **插桩** — 一次只验证一个假设，优先用断点，其次用带标签的临时日志。
5. **修复 + 回归测试** — 先写回归测试，再修 Bug。
6. **收尾** — 跑原始复现回路，清理调试代码，把正确的假设写进 commit 信息。

**适用场景**：遇到难 Bug、性能问题、间歇性失败。

---

### /grill-with-docs — 需求采访 + 文档生成

**用途**：在动手编码前，通过密集的问答把需求聊透，同时自动更新领域文档。

**流程**：
- 逐问采访，每次一个问题，等待你的反馈
- 对照已有的 `CONTEXT.md` 术语表检查用词一致性
- 发现模糊语言时直接追问："你说的'账户'是指客户还是用户？"
- 术语一旦确定，当场写入 `CONTEXT.md`
- 遇到满足条件的重大决策时，建议创建 ADR（架构决策记录）

**适用场景**：新功能开发前、需求不清、想完善项目文档。

---

### /grill-me — 纯需求采访

**用途**：和 `/grill-with-docs` 一样密集采访，但**不生成文档**。只聊透需求。

**适用场景**：非代码任务的设计讨论、不需要文档的快速对齐。

---

### /tdd — 测试驱动开发

**核心原则**：测试应该通过公共接口验证行为，不绑定实现细节。好的测试读起来像规格说明——"用户可以用有效购物车结账"比"调用 checkout 函数返回 true"好得多。

**流程**：
1. **规划** — 确认接口设计、要测试的行为、深度模块的机会
2. **示踪子弹** — 先写一个测试→失败→写最小代码→通过，证明整条链路通了
3. **增量循环** — 逐行为 RED→GREEN，每次只加一个测试和一个实现
4. **重构** — 所有测试通过后提取重复、深化模块

**重要**：垂直切片，不要水平切片。不要一次性写完所有测试再写所有实现。

**适用场景**：新功能开发、Bug 修复（希望用测试锁住的）、任何想用 TDD 方式推进的工作。

---

### /improve-codebase-architecture — 改进代码架构

**用途**：发现代码中的"浅模块"（接口和实现一样复杂），提出深化重构方案。

**核心概念**：
- **模块**：有接口和实现的任意单元（函数、类、包、切片）
- **深度**：接口小但功能多的模块叫"深模块"（好），接口和实现差不多复杂的叫"浅模块"（需要改进）
- **接缝**：可以不修改原代码就改变行为的地方
- **删除测试**：想象删掉这个模块——如果复杂度消失，它是透传；如果复杂度分散到 N 个调用方，它有价值

**流程**：
1. 探索代码库，找架构摩擦点
2. 列出深化方案（每个包含涉及文件、问题、方案、好处）
3. 你选一个方向，进入问答深挖

**适用场景**：代码库越来越乱、想做重构、排查可测试性差的问题。

---

### /zoom-out — 宏观视角

**用途**：让你从更高抽象层理解不熟悉的代码区域。给出相关模块和调用方的地图，使用项目领域术语。

**适用场景**：看陌生代码、想知道某段代码在整个系统中的位置。

---

### /to-prd — 从对话生成 PRD

**用途**：把当前对话上下文中已经讨论好的内容合成为一份 PRD（产品需求文档），无需再次采访。

**流程**：
1. 探索代码库当前状态
2. 梳理需要构建/修改的模块
3. 用模板生成 PRD（包含问题陈述、方案、用户故事、实现决策、测试决策、范围外）

**适用场景**：聊完之后想形成正式文档存档。

---

### /to-issues — 拆分任务为 Issue

**用途**：把计划/PRD 拆成可以独立领取的垂直切片 Issue。

**核心概念**：垂直切片 = 贯穿所有层的窄通道（Schema → API → UI → 测试），每个切片完成一条完整行为。HITL 类型需要人工介入（架构决策、设计审查），AFK 类型可完全交给 Agent。

**流程**：
1. 从对话上下文收集需求
2. 拆分成垂直切片（标题、类型、依赖、对应用户故事）
3. 与你确认粒度和依赖关系
4. 按依赖顺序发布到 Issue 追踪器

**适用场景**：大任务拆解、分配工作。

---

### /triage — Issue 分类

**用途**：按状态机处理 Issue 流转（待评估 → 等待反馈 → Agent 可做 → 需人工 → 不予处理）。

**适用场景**：管理 Issue 队列、处理新提交的 Bug/需求。

---

### /prototype — 原型验证

**用途**：写一次性的原型代码来回答设计问题，分两个分支：
- **逻辑原型**：构建可交互的终端小程序，验证状态机/数据模型
- **UI 原型**：在一个路由上生成多种截然不同的 UI 变体，通过 URL 参数切换

**规则**：明确标记为一次性代码、一个命令就能运行、不持久化、不写测试、用完即删或纳入正式代码。

**适用场景**："这个逻辑对不对？"、"这个界面应该长什么样？"

## 效率类技能

### /caveman — 极简模式

**用途**：大幅压缩 Agent 输出的 Token 用量（约减少 75%）。去掉冠词、填充词、客套话，保留全部技术准确性。

一旦触发，持续生效，直到你说"stop caveman"或"normal mode"才会恢复。

**适用场景**：想要极简回答、省 Token、批量操作。

---

### /write-a-skill — 创建新技能

**用途**：创建新的 Agent 技能，包含正确的结构、渐进式披露和打包资源。

**适用场景**：想把自己的工作流变成可复用的技能。

---

## 配置类技能

### /setup-matt-pocock-skills

**用途**：初始化仓库配置（Issue 追踪器、Triage 标签、领域文档布局），其他技能依赖此配置。每个仓库只需运行一次。
